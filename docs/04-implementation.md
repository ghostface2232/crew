# 04. Implementation Notes

Written 2026-11-11. Records the implementation of Phase 1 (bridge) and Phase 2 (status board) from [02-implementation-plan.md](02-implementation-plan.md), along with what changed from the plan and why. AgentGauge integration (Phase 3, [document 03](03-agentgauge-integration.md)) was left out of this round.

All facts about external tools were verified directly on this machine on 2026-11-11 against Claude Code 2.1.321, Codex CLI 0.167.0, Antigravity CLI 1.5.5, and Node.js 24.22.1.

## 1. Architecture

```
Claude Code (Desktop or CLI) ── Lead
  │ stdio MCP                    │ Hooks (HTTP)
  ▼                              ▼
plugin/bridge/mcp.ts ──HTTP──▶ Crew Daemon (127.0.0.1:47615)
                                 ├─ codex app-server   (Codex: implementation, review)
                                 ├─ agy acp            (Antigravity: copy & doc cleanup)
                                 ├─ Event log ~/.crew/events.jsonl
                                 └─ Status board (SSE) http://127.0.0.1:47615
```

- A single daemon owns worker processes, job state, event log, and status board; the MCP server is a thin stateless client, so jobs survive Claude session restarts or compaction and multiple sessions share one board.
- The daemon starts automatically with the MCP server and replaces itself on the next call if `bridge/` file hashes differ on disk, so edits take effect without bumping the version. If jobs are active, replacement waits until idle: the client sends `POST /api/shutdown` with `ifIdle`, and the daemon returns `409` while any mutating POST is in flight or a job is running, starting, syncing, changing rounds, or being discarded (since the client's health check may be stale). A daemon from another folder is replaced only when the caller's version is newer. `crew daemon stop` and `restart` stop the daemon unconditionally; if shutdown goes unanswered, they kill the PID in `~/.crew/daemon.json` (provided it matches the port listener) and report an error instead of "running" if the daemon stays up or rejects `~/.crew/token`. Replacement never spawns a new daemon while the old listener is up. If the PID file is missing, stop retries briefly and reports that the PID could not be confirmed; after a forced stop, it removes the file only if it still names the stopped PID (Windows SIGTERM bypasses shutdown).
- The daemon binds the port before reading or writing anything else, so a concurrent loser exits without creating a token, loading jobs, or clearing active scratch directories and review snapshots. Ports held by the system with nothing listening (WSL mirrored networking reserves 4096 ports per start) are skipped down `PORTS` in `config.ts`; clients, hooks (`bridge/report.ts`), and the app look up the bound port in `~/.crew/daemon.json`.
- Everything is packaged as a single Claude Code plugin (`plugin/`) containing the MCP server, hooks, 4 skills, 1 subagent, and 9 role files.

## 2. Tools used by the lead

| Tool | Behavior |
| --- | --- |
| `delegate` | Hand an implementation slice to Codex in a dedicated worktree (`~/.crew/worktrees/<repo>/<job id>/<repository folder>`) on branch `crew-<job id>` |
| `review` | Hand a read-only review to Codex. Defaults to adversarial; `mode: "standard"` uses Codex's built-in review |
| `polish` | Hand copy, comment, and doc cleanup to Antigravity. Edits outside `targets` are reported as out of scope |
| `status` | Return a bounded job summary, a report page, or active and recent jobs plus every agent's usage |
| `wait` | Wait for a job to finish. If an approval request or question arrives meanwhile, prompt the user in the app and keep waiting |
| `reply` | Send follow-up instructions to the same worker session, or forward an approval/denial that the user gave in chat |
| `cancel` | Cancel a job. With `discard: true`, remove the finished job's worktree and branch |

- Added `wait` and `reply` to the five tools from document 02 section 3.4 for parallel implementation and multi-turn revisions.
- Job tools (`delegate`, `review`, `polish`, `reply`) return the job ID at once by default; `background: false` blocks until the worker ends or needs the lead. The lead ends its turn instead of sitting in `wait` so the user can keep talking to it; the wake hook brings it back when a job ends, needs a decision, or asks a lead question.
- Gitignored paths listed in `.worktreeinclude` at the repository root (`.gitignore` syntax, shared with Claude Code's native worktrees) are attached to the `HEAD` worktree so workers can run tests (such as `node_modules` and `.env`) without reinstalling dependencies. Files are copied; directories use forced copy-on-write (`cp -cR -P` on macOS, Node's `COPYFILE_FICLONE_FORCE` elsewhere), falling back to a junction on Windows or a symlink elsewhere when cloning is unsupported (`ENOTSUP`, `EOPNOTSUPP`, `EXDEV`, `ENOSYS`, `EINVAL`, or macOS `clonefile failed: Operation not permitted`, which on 2026-11-14 refused every file for about two hours on a working volume). Unreadable sources and other errors still fail. Crew records links on the worktree and job notes, excludes them by pathspec in commits and dirty checks (directory-only ignore rules miss symlinks, and `info/exclude` is shared with the user's checkout), tells workers they are shared read-only with the main checkout (do not install into or delete them; put tool caches in temp), and marks each link and resolved target read-only in Codex's permissions profile (keeping broken links read-only with missing targets omitted). Because shared targets stay unchanged across turns, loaded threads continue without forced resume.
- Although the daemon is shared across sessions, each job belongs to its starting project; argument-less `wait` and `status` filter to the caller's project, while the status board and `crew status` show all projects.
- Workers cannot commit because worktree git metadata sits outside their sandbox; when a job finishes, the bridge commits to the job branch and the lead inspects the diff to merge or reject it.

Before removing a worktree or review snapshot, Crew detaches recorded shared links on every platform; on Windows it walks with `lstat` and detaches every symlink and junction before Git removal or fallback. Recursive cleanup (scratch on turn end/restart, failed include copies) also detaches links first using `unlink`, or non-recursive `rmdir` for a directory-style junction, never descending into targets. [Node 22.18's bundled libuv](https://github.com/nodejs/node/blob/v22.18.0/deps/uv/src/win/fs.c) reports reparse points as links for `lstat`; a resolved-path check also guards directory-style junction reports.

On Windows, removal next clears read-only attributes on the worktree and its validated Git admin directory (strictly inside the common Git directory's `worktrees/`; other metadata is refused). Two hidden-window calls clear the root and contents (`attrib -R <path> /D /L`, then `attrib -R <path>\* /S /D /L`, skipping the recursive call for empty directories), avoiding a process per directory ([attrib docs](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/attrib); `/L` targets links themselves). Clearing is best-effort (localized warnings, hidden/system messages, nonzero exits, or missing `attrib` do not stop removal) and Crew preserves ACLs including OneDrive policy without running `icacls /reset`, since sandbox SID deny ACEs do not apply to the daemon's user token.

Before discard or automatic snapshot removal, Codex releases the thread and tracked child subscriptions with `thread/unsubscribe` (confirmed in CLI 0.167.0's v2 schema on 2026-11-14). [Codex's lifecycle](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/app-server/src/request_processors/thread_lifecycle.rs) delays unload until idle without subscribers, so immediate handle release is not guaranteed and threads held by another app stay open; later reviews resume saved sessions. Windows removal retries transient `EBUSY`, `EPERM`, `EACCES`, and `ENOTEMPTY` with bounded backoff. On failure, fallback removes only the validated admin directory after preparation and verifies Git no longer lists the worktree, never running repo-wide prune during discard. If cleanup still fails, Crew deletes the branch only if the worktree is unlisted and the branch is not checked out, keeps the worktree record, and records the original error plus remaining directory, admin directory, and branch in status and results pointing to `crew gc`.

Because Codex apps group threads by working directory, each worktree shows as its own project; at most once a day on `app-server` start, Crew archives its worktree threads quiet for seven days (`thread/list` oldest first, then `thread/archive`), leaving live runs, resuming replies, and threads open in another client. Archived threads stay readable, and `reply` calls `thread/unarchive` before resuming.

`crew gc [--apply] [--branches]` scans remembered repositories in dry-run mode by default, listing orphan worker directories, missing-worktree admin directories, and unused worker branches with merge status against `HEAD`. `--apply` removes directories and prunes metadata; `--branches` (with `--apply`) deletes only branches merged into `HEAD`, keeping unmerged branches with the exact `git branch -D <name>` command. Paths are compared by realpath (resolving existing parents for missing paths) and must stay inside Crew's `worktrees/`, use Crew worker naming, and have no owning job unless marked by a failed discard. A job's slot holds its worktree under the repository folder name (or directly as the slot in older layouts) and is kept whole while Git registers any worktree inside it, a job owns a path inside it, or a `.git` file points to existing admin metadata. Repositories with an active job, discard, snapshot refresh, or round change are skipped, and workspace changes cannot start during gc; jobs with incomplete cleanup refuse follow-ups, sync, and round changes until gc resolves leftovers. Global Git prune is skipped if it could remove unrelated or owned metadata, and validated admin paths survive missing `gitdir` pointers so gc can prune recorded leftovers while protecting unidentifiable metadata. Completed cleanup clears the failed discard record while keeping any unmerged branch visible as a leftover. User-authenticated `POST /api/gc` accepts `{ apply?: boolean, branches?: boolean }` and returns `{ text: string }`; CLI output is plain text.

Checked on macOS/APFS on 2026-11-14 with Node 24.22.1 (libuv 1.52.1): `COPYFILE_FICLONE_FORCE` returned `ENOSYS` even on a regular APFS file while `/bin/cp -c` succeeded, and cloning `/dev/null` failed with `clonefile failed: Invalid argument`, so macOS uses `/bin/cp -c` instead of treating `ENOSYS` as an unsupported filesystem. Injected clone-failure tests cover link creation, Codex permissions, detachment before removal, and keeping main-checkout `.bin` files intact. Windows behavior uses fixtures rather than a live Windows run; HTTP auth and CLI checks use an isolated daemon, temporary Crew home, free port, and fake agent without starting a live worker.

### Lead delivery (step 1)

The daemon owns delivery state in `jobs.json`. Each job records the starting MCP server's `CLAUDE_CODE_SESSION_ID` as `lead`; board and legacy jobs start unowned. When a session's Crew call shows a job, the MCP server adopts it before offering news, and the wake hook adopts job ids seen in tool responses (covering servers without a session id). Completions, failures (including restart recovery), lead questions, and decision requests append an immutable news snapshot with a per-job `newsSeq`; progress does not. Running jobs silent past `stallSeconds` show as stalled on the board at once, and adapters with `probe` check them: Codex reads `thread/read` runtime status (sub-agents first) and re-reads non-active threads after a pause. Active turns clear the stall without a wake, ended sub-agents stop blocking parent completion, and certainly-ended parents without a `turn/completed` fail the job (creating failure news); failed checks or adapters without `probe` add one `stalled` news item per stall so the lead wakes to check, steer, or cancel.

Only an echoed receipt acknowledges news; every lead tool accepts `ack: "<receipt>"` or an array of receipt ids and processes them before doing work or offering new news. Tool responses and hook digests are offers, not acknowledgements. Receipts cover exactly the `(jobId, newsSeq)` snapshots in that digest and stay verifiable after the offering lease expires. ACK validates receipt, session ownership, and revisions so old receipts cannot consume later news. `ackedSeq` is the contiguous acknowledged prefix, and `delivered` projects it onto event sequence numbers for legacy board/native readers (`/delivered` no longer accepts sequence ACKs). Delivery mutations save synchronously before an offer or ACK succeeds, rolling back on save failure.

Automatic offers share one 30-second offering lease per session and retry each news item at most twice, even across process crashes or daemon restarts. Explicit tool reads issue receipts without spending that budget and replace the current offering lease while keeping older receipts valid; exhausted news stays unacknowledged in status and on the board. One watcher lease per session lasts at most 60 seconds, renews during polling, and is bounded by the hook deadline. New hooks exit if a healthy watcher exists, replace one within 15 seconds of its deadline, or take over an expired lease; generation checks fence replaced watchers from renewing, releasing, or offering.

News also comes from watched pull requests (section 5.5): a watch is a delivery subject like a job, its receipts carry its id in `jobId`, and a session cannot adopt one.

Crew tool hooks, Stop, and SessionStart (`startup`, `resume`, `clear`, `compact`) arm `wake.ts watch` with `asyncRewake`. SessionStart is needed because watchers die with their Claude Code process when Desktop ends idle sessions under memory pressure and resumes them later. Watchers query authenticated `/api/lead/*` routes, never inspect tool output, retry connection failures with backoff, and wait through occupied offering leases. Dead watchers lose their lease after 25 seconds, or immediately if a long poll is cut off early, so resumed sessions re-attach at once. Synchronous Stop offers pending news with exit 2 unless `stop_hook_active` is set; SessionStart (`startup`, `resume`, `compact`) and UserPromptSubmit inject a bounded list of pending ids via `additionalContext` without an offer or ACK. Unauthenticated `/api/hooks/claude` only ingests activity. Session identity scopes query/ACKs, while the shared daemon token authenticates access across sessions.

Hook timeout is 86,400 seconds and the watcher exits cleanly 10 seconds earlier. **Verify this finite timeout and asyncRewake behavior on the installed Claude Code/Desktop host before relying on that lifetime.** Killed hooks do not re-arm themselves; persisted unacknowledged news remains recoverable by an active watcher, the next hook, or board/status.

Digests hold at most eight snapshots, and every MCP tool response (envelope plus images) fits within 32 KiB: tool text takes at most 24,000 bytes and a report page 16,000, leaving omitted images in the evidence list and on the board. Omitted news gets no receipt or attempt count. Read long reports via `status(job_id, report_offset: 0)` using the returned UTF-16 offset (never splitting surrogate pairs) and optional `turn`; receipt instructions sit outside the truncated summary. Delivery tests cover crashes before output, lease expiry and replacement, ownership, restart recovery, snapshot ACKs, attempt budgets, persistence failures, and escaped Unicode limits.

### 2.1 Role assignments

Each tool is a role, and `roles` in `~/.crew/config.json` names the agents that hold it. With no `roles` entry the defaults apply, which are the original fixed roles (requirement R3).

```json
{
  "roles": {
    "delegate": { "agents": ["codex"] },
    "review": { "agents": ["codex"], "codex": { "effort": "high" } },
    "polish": { "agents": ["antigravity"] }
  }
}
```

- `agents` lists `codex`, `antigravity`, or `claude` ([09](09-usage-presets-rounds.md) section 15). Optional `codex` and `antigravity` overrides (`model`, `effort`) override global agent settings for that role, and tool arguments override both. Antigravity's effort sets `thought_level` after the model because levels differ by model, stepping down to the nearest lower supported level; sessions keep their own level when effort is omitted, unknown, or unsupported. The earlier form (`agent`, `also`, `model`, `effort`) is still read.
- `polish` takes `model` like `delegate` and `review`, and text results put `model:` right after the title. Optional `resolvedModel` and `resolvedEffort` record what the session reported (falling back to configured values, or `unknown (agent default)` when neither is known; older jobs still load). Codex reports both on thread start or resume; Antigravity reports its model in ACP session config, legacy model state, or config updates.
- Work roles open their report with `## Outcome` (`done`, `partial`, or `blocked`), saved in `Job.outcome` for the latest turn (cleared on new turns; reviews, debates, and questions omit it). Results pair it with bridge observations: `outcome: done as declared, but the bridge check failed` (or noting no files changed after a refusal or decline), or `outcome: not declared` when missing.
- When a job changes nothing and its latest turn had a refusal or declined action, the result points to the refusals/notes (earlier turns do not count). Acceptance lines list kept round commits for cherry-picking, omitting that hint when none is known.
- Antigravity allows Crew's six worker tools (`ask_lead`, `lead_answers`, `siblings`, `search`, `recent_changes`, `rate`) when matched by MCP metadata or exact `mcp_crew_<tool>` title (with or without `Run `). Revised 2026-11-20: `mcp_crew_<8 hex digits>_<tool>` is matched too. One `agy acp` process serves every job, each job registers a server named `crew` with its own environment, and from the second job on agy 1.5.9 tells them apart by that suffix; the bridge refused those calls, so the first Crew tool an Antigravity worker called ended its turn. Reproduced with two jobs on one daemon, where the requests carried the title alone and no MCP metadata. Title matching applies only to `other` calls lacking conflicting MCP metadata or command input (`rawInput` string, `command`, `CommandLine`); `execute` and unrecognized editor calls still follow role policy. Because the Windows refusal lacked a captured ACP request, title matching is covered by a fixture rather than a live run.
- The table is read at job start so edits apply to the next job without a restart; invalid tables (unknown role, setting, or agent, or wrong type) fail the job with the reason instead of falling back to defaults or prior assignments. Other settings still load at daemon startup.
- Role text (`plugin/roles/engineer.md`, `reviewer.md`, `polisher.md`) names no agent. Codex receives it as `developerInstructions`; Antigravity receives it via `_meta.antigravity.systemPrompt.append` when advertised, else at the top of the first prompt (resent on session restore).
- The lead's tool titles and server instructions name role holders as of session start; `status` and job results name the agent that actually ran.
- The board shows role holders and updates when the file changes.

Every Codex job—including writable and `runs_app` jobs—gets a fresh per-turn scratch directory writable in its sandbox with `TMPDIR`, `TMP`, and `TEMP` set via `shell_environment_policy.set` ([09](09-usage-presets-rounds.md) section 9), while read-only and `runs_app` profiles keep their restrictions. The system temp directory is not made writable because Codex resolves it to its server `TEMP` and on Windows grants write via an inherited ACL over every file there (on 2026-11-19, ~305,000 entries exceeded the 180-second `thread/start` timeout and failed every `runs_app` job). Antigravity shares one server process with no per-job environment, so its environment is unchanged.

Scratch clears after every turn; files a Codex worker needs across turns or wants the lead to have go in `work` inside the job's evidence directory (only top-level images and videos in the evidence directory list as evidence). Antigravity jobs have no scratch and no `work` folder.

Workers launch their Crew MCP server using the daemon's own executable (under the desktop app, the Electron executable); because agents launch without `ELECTRON_RUN_AS_NODE`, the server's environment sets it so it does not open the app and fail the handshake.

Without startup tracking, a worker whose Crew server fails to start silently runs without `ask_lead`, `browser`, and the rest (0.3.0 did this on Windows until a retrospective). Codex emits `mcpServer/startupStatus/updated` (`name`, `status`, `error`) per thread; when `crew` fails, the job gets a note and board activity once per run (held if it arrives before `thread/start` returns). Checked 2026-11-20 with Codex CLI 0.167.0 and a nonexistent server command: `failed` arrived in the same second as `thread/start` twice with no turn started. Antigravity reports no such status, so its jobs are uncovered.

What each agent may do in each role:

| Role | Codex | Antigravity |
| --- | --- | --- |
| `delegate` | `workspace-write` sandbox; approvals follow `codex.approvalPolicy` | Reads anywhere, edits inside the worktree. Every other action (commands, deletes, moves, network) is put to the user as an approval, unless the request omits its input, in which case it is refused |
| `review` | `read-only` sandbox, never prompts; with `runs_app`, a writable sandbox in a snapshot worktree, with approvals as for `delegate` (section 5.4). `mode: "standard"` uses Codex's built-in review | Reads only. Edits and commands are refused and listed in the job's notes. Because it cannot run git, the bridge saves a diff under `~/.crew/reviews/` for each turn (removed when the turn ends) and the job notes say that no tests or checks were run. Follow-ups regenerate the diff for the saved review target and receive its new path, including after a bridge restart. Older jobs without a saved target require a new review. `mode: "standard"` falls back to the prompted review, also noted. Needs a git repository |
| `polish` | `workspace-write` sandbox. Scope is checked after the fact: files outside `targets` are reported as out of scope | Reads anywhere, edits inside the worktree. Everything else is refused |

Antigravity approvals follow Codex approval rules (section 5.1): user answers, full request fields and job workspace shown, one at a time in arrival order, and only "allow once" sent (or "reject once" on denial when offered). Cancelling the job, turn end, or server exit cancels open requests. No role may switch Antigravity's mode because "accept-edits" skips per-edit path checks (section 10).

Verified on 2026-11-12 with Codex CLI 0.167.0 and Antigravity CLI 1.5.5, in a throwaway repository on a separate daemon, with the roles swapped:

The approval showed the whole request: Antigravity sends the command as `rawInput.CommandLine` alongside other fields, so the prompt prints the full input as JSON. After approval the tests ran, and the bridge committed the result on the job branch |

Not exercised against the real services: denying an Antigravity request, a request without `rawInput`, and a mode switch. These are covered by protocol stubs only.

### 2.2 Shared instructions

Instructions written once reach every agent (requirement R9).

| File | Applies to |
| --- | --- |
| `~/.crew/instructions.md` | Every project |
| `.crew/instructions.md` at the repository root | That project. Read last, so it can refine the global file |

- Workers: both files are read when a job starts and appended to the job's instructions after the role text, with a preface saying they apply within the role and do not widen it. Codex receives them in `developerInstructions`, Antigravity with the role text (above). `status` lists the files a job was given.
- Claude: a `SessionStart` and `SubagentStart` command hook (`bridge/context.ts`) prints them as `additionalContext`, so the lead and its subagents have them too. It runs again after compaction. The text tells the lead that workers already have the instructions, so delegated tasks need not repeat them.
- The project file is looked up in the repository's main working tree, for a worker job and a Claude session alike, even when either starts inside a linked worktree or a subdirectory. An uncommitted edit therefore applies to the next job. Outside a repository, the session's project directory is used.
- Nothing is written to any service's own instruction files (`AGENTS.md`, `CLAUDE.md`, rules folders).
- A missing or empty file means none. A file that exists but cannot be read fails the job with the reason. The hook reports any failure of its own (unreadable file, git error, malformed input) in the session instead of exiting quietly.
- Claude Code replaces hook context over 10,000 characters with a 2,000-character preview. A file that would take the total past 9,000 characters is replaced by its path, with a statement that none of it is in context until read; files that fit are still sent whole. A cut-off copy is never sent, because it would look complete. Workers have no such limit in the bridge.
- A project file is part of the repository, so it is trusted to the same degree as that repository's `AGENTS.md` or `CLAUDE.md`, and may have been written by someone other than the user. Each part is therefore headed by where it comes from. It cannot widen a role: what a role may do is enforced by the bridge and the sandbox, not by the text. It can still steer an agent within its role, and because it is read last it can contradict the global file.

Verified on 2026-11-12 with marker instructions in both files (write in English, end with a fixed line, use a given word in the first sentence): a Codex review, an Antigravity polish, and a headless Claude Code 2.1.321 session each followed or quoted both. The Codex report came back in English although the same setup had reported in Korean before, so shared instructions took precedence over the user's own Codex defaults in that run.

Not verified: whether `SubagentStart` context reaches a real subagent (the hook's output for that event was only checked by running the script), whether Claude Code counts the 10,000-character cap per hook or across all hooks of an event, and whether Codex's built-in review mode honors `developerInstructions`.

## 5. Status display and stall detection (R5)

- Event shape adds `job_id` and a sequence number to the proposal in document 02: `{seq, ts, agent, session_id, job_id, kind, detail}`, where `kind` is `started`, `progress`, `waiting`, `error`, `limit`, `stalled`, `done`, or `cancelled`.
- Quota exhaustion: emits a `limit` event based on `codexErrorInfo` (`usageLimitExceeded`, `rateLimitExceeded`, `sessionBudgetExceeded`) on turn errors for Codex, error text for Antigravity, and `error: rate_limit` from the `StopFailure` hook for Claude.
- Stalls: a running job that emits no events for 5 minutes is marked `stalled`. For Claude sessions, the timer applies only when no tool call is actively running.
- `waiting`, `error`, `limit`, and `stalled` also trigger system notifications: through `osascript` on macOS, and on Windows as a toast shown through Windows PowerShell 5.1 under its own app identity, with the text passed in environment variables.
- Codex usage is read via `app-server`'s `account/rateLimits/read` and `account/rateLimits/updated` and shown on the board and in `status` (the supplemental path in document 03 section 9). It is not yet used for routing decisions.

### 5.1 Approval requests and questions

Codex approval requests go first to its automatic reviewer (`codex.approvalsReviewer`, default `auto_review`). Anything it refuses twice, and every request or question reaching Crew, goes to the user rather than the lead. The lead never approves, though it may decline an out-of-scope request with a reason (`reply` with `decision: "decline"` and a message), which grants nothing and spares the user an unnecessary prompt. The worker receives the decline and reason, and job notes and activity record it; if delivery fails, the job notes it and the lead sends it via `reply` after the turn.

- While the lead waits inside a job call (`delegate`, `wait`, etc.), the MCP server sends an elicitation request so the Claude app shows its native input prompt; the user's answer goes straight to the worker and the call continues.
- For background jobs, the wake hook wakes the lead and the prompt appears when it calls `wait`.
- If answered first via the status board, or if another job finishes and returns the call early, the in-app prompt is withdrawn immediately.
- When multiple jobs wait at once, prompts appear sequentially; any already answered on the board while an earlier prompt was open are skipped.
- If the user dismisses the prompt, the app fails to show it, or the client lacks elicitation, the waiting state returns to the lead with distinct guidance so it asks the user in chat.
- Antigravity requests follow role policy (section 2.1), so only an engineer's commands reach the user. Its questions arrive as `elicitation/create` form prompts: answers matching a choice by text or number select it, free text passes as written, and declining declines the form.

**Allow for This Job.** Codex plugin tools prompt before each call, so computer-use jobs ask `Allow Computer Use to use "<App>"?` on every screenshot, click, and key press. Requests matching `Allow <who> to use "<target>"?` (`waiting.grant` names the target; no scope is guessed for others) offer *Allow for this job* beside Approve and Deny on the board, in the app, in the in-app prompt (`allow_for_job`), and via `reply` (`decision: "allow_for_job"`, only when the user said so). Choosing it approves the request and stores a grant keyed by MCP server and message (excluding tool name) in the running adapter for the whole job—covering sub-agents and follow-up turns, but not other apps, servers, jobs, or daemon restarts. Matching queued and later requests auto-approve and log to job activity (`allowed for this job: click · Computer Use using "<App>"`). Command, file, and permission approvals, read-only jobs, and Codex's automatic reviewer are unchanged.

**The automatic reviewer and refusals.** Crew starts every Codex thread with `approvalsReviewer: auto_review`, so Codex's built-in reviewer answers approval requests without reaching Crew. Set `{"codex": {"approvalsReviewer": "user"}}` in `~/.crew/config.json` to route all requests to the user; Antigravity has no built-in reviewer and relies on role policy (section 2.1).

When the reviewer refuses an action (`item/autoApprovalReview/completed` with `denied` or `timedOut`), the bridge records action details (executable argument boundaries, working directory, and MCP input recovered from the started item by `targetItemId` in the same thread/turn or marked missing) on the job and result. Prompts and refusal notes show action fields instead of raw protocol payloads, omit environment fields, and cap free-form input at 4,000 characters, reasons at 2,000, and full descriptions at 8,000 (`… (truncated)`).

Missing reasons are labeled missing, and generic messages such as "blocked by policy" are quoted and marked generic rather than expanded, with the result suggesting an in-bounds alternative alongside the retry path below. Declined Codex approvals, Antigravity role refusals, user declines, and missing one-time approval options keep the same action input, paths, and next step; ACP responses still pick reject-once (or cancel if unavailable) since that protocol takes only an option id. Workers are instructed to report the exact command or tool input and message received (Crew's source had no "blocked by policy" string; a provider or worker can supply it, though Windows reports did not capture its source). The lead then decides whether the user's conversation request covers the action:

1. If it does, the lead calls `reply` with `approved_by_user`, quoting the user's words without asking again; the bridge sends a follow-up stating the approval and refused action for another automatic review.
2. If refused again, the same call starts a turn with `approvalsReviewer: user` so requests go to the user, then later turns return to `auto_review` ("again" means the prior turn was itself a retry; an unrelated later refusal restarts with `auto_review`, and a retry failing before acting keeps the refused action on the job).
3. If the request does not cover the action, the lead tells the user and lets them decide.

The first retry relies on the lead's reading because the reviewer treats the follow-up as the user's message. Checked 2026-11-12 via `codex app-server`: the reviewer read the thread's user message as authorization ("authorization: high") and approved deleting an external folder requested by the task; `denied` is covered only by stub-server tests.

### 5.2 Deciding from the board

The board is also where the user reads what happened and acts on it (requirement R10, roadmap item B1).

- **Job details.** Clicking a job card, title, or feed job name opens a side sheet (`#<job id>`) showing agent, model, project, branch, tokens, shared-instruction files, changed files (out-of-scope marked), notes, report, task, and job activity.
- **Evidence side by side.** Pressing a capture opens that one alone; a strip of the job's captures below it adds others beside it and takes them away, so the user picks what a result is judged against. At most four panes appear—ordered lead reference, then by turn, a `<view>-before` ahead of its `<view>-after`—up to three in a row or a 2×2 grid at one height without outlines. Captions state each capture's turn against total turns ("Turn 1 of 3") in the sheet, details, and app; modifier-click opens the file alone. The macOS app does the same in its own sheet, decoding images at pane size rather than handing them to Preview, while recordings open in the system player (no WebM decoder on macOS); context menus open files in their default app or Finder.
- **Follow-up.** The sheet sends a message continuing the same worker session (the board's counterpart to `reply`), notifying the lead when the turn ends.
- **Answers in words.** Worker questions take text answers from the card or sheet; approvals keep Approve, Deny, and Allow for this job on target-naming plugin requests (section 5.1). Answers carry the request id so they cannot settle a later request.
- **Updates do not disturb.** Cards and sheet sections re-render on updates while preserving typed text, caret, focus, opened sections, and send status, deferring during IME composition. Answer text binds to its request and follow-up text to its job.
- **Failures are said.** Unopenable jobs, refused copies, and stale form sends report in a line at the top of the board.
- **Activity by job.** Feed rows name and link to their job so same-agent jobs are distinct.
- **Projects.** The board organizes work by command inside alphabetical project groups (not by agent), showing lead sessions (one line each), commands, and running/waiting counts; groups do not reorder on updates. Jobs and sessions belong to the repository's main working tree even when started from a subfolder or worktree. The top bar or a project heading filters the board and feed to one project (remembered in the browser) and shows waiting counts; with all projects shown, feed rows name their project.
- **Pending count.** The tab title shows how many jobs and sessions wait on the user across all projects.
- **Settings.** A sheet edits roles (agent, model, effort) and shared instructions (global or per-project), writing `~/.crew/config.json`, `~/.crew/instructions.md`, and the main tree's `.crew/instructions.md`. Role saves keep other settings and refuse unparseable files; project writes allow only daemon-known projects and never follow symlinks at `.crew`, the instructions file, or temp names. Closing with unsaved edits asks first.
- The resume command moved from the card footer into the sheet next to a diff command.

Checked on 2026-11-12 in the built-in browser pane against a separate daemon with stub agents: opening a job from a card, the feed, and a link; answering a question in words; a follow-up turn; a job update arriving while an answer was half typed (text, focus, and caret kept); project groups and the project filter with two projects, including a job started from a subfolder; saving roles and per-project instructions and reading the files back; refused writes (unknown project, foreign origin, unknown agent); dark mode and a phone-width pane. Not checked: a screen reader, typing with an input method, and browsers other than the built-in pane. Automated board-handler tests cover instruction saves with concurrent edits, failed requests, and editor reloads. The remaining board behavior was checked by hand as listed.

### 5.3 Missions: a command as one unit

A mission is one user command that the lead takes through the pipeline (requirement R10, roadmap item B2). It answers "what was this command split into, who has each part, and how far along is it" without opening a session.

- **Reported by the lead, not inferred.** The lead calls `mission` with `title` and a nonempty `stages` plan (up to 30 steps from `plan`, `implement`, `self-review`, `cross-review`, `fix`, `polish`, `final`; repeats allowed). `stageIndex` tracks the current occurrence (`stage` mirrors it). Passing `stage` advances to its next occurrence after `stageIndex` or inserts it right after if none remains (repeating the current step is a no-op, as when resumed; skipping planned steps drops them). Resending the same title resumes and ignores `stages`; starting without `stage` uses index 0 (or selects/inserts after step 0). Open missions auto-attach new jobs.
- **Fluid plans.** Passing `stages` again replaces only steps after `stageIndex` (`[]` drops the rest) without altering the passed/current prefix, keeping history and job indices stable (e.g., after `self-review`, `[final]` drops `polish`; `[fix, cross-review, final]` adds repair and review). The result prints the full plan with the current step marked, and the lead calls `done: true` with an outcome once work finishes (`abandoned` if dropped).
- **Named stops.** Plan entries may append `: <name>` (up to 24 chars, e.g., `implement: Sample`), shown in place of the stage name without numbering while the stage still decides job attachment. Names store in `labels` (`null` where unnamed, omitted if none) so `stages` stays compatible for older clients. Named stops let the lead advance between repeated stages by case-insensitive name; unknown names insert after the current step.
- **On the board and in the app.** Missions render only their planned stops in order—labelled Plan, Build, Review (shared by both review stages), Fix, Polish, Final—with subsequent repeats numbered (`Review 2`, `Fix 2`). Prior stops are passed (all on `done`), and the lead sits at the current stop. Daemon-assigned `missionStep` pins each job to its requested index across later rounds or revisions; legacy jobs attach by kind (preferring current match, first match, then current stop). Ended missions start folded, clicking a job opens details, and ungrouped jobs stay separate.
- **Progress and compatibility.** Planned missions compute progress as `(current zero-based index + share) / plan length`, where `share` averages `0.5` for running/waiting unfinished jobs and `0` for other unfinished jobs (`0.5` if none), reaching 100% only when `done`. Missions without `stages` keep the six-stop combined-review track and seven-stage formula without migration; adding a remainder turns original stages through the current one into the preserved prefix.
- **Closing and quiet missions.** Active missions offer Mark Done and Stop Tracking in both UIs (shown in the native app once a mission looks finished, and Mark done on abandoned ones too). Mark done sends `done: true` with “Marked done on the board.” or “Marked done in Crew.” (requiring `reopen: true` on abandoned missions so late lead `done` calls cannot undo Stop tracking). Stop tracking marks abandoned and leaves jobs running (its tooltip notes it does not mark done). Clients show “Looks finished” after 20 quiet minutes with no active jobs unless the owning lead session is still working (stored state unchanged; empty missions qualify too). Job activity updates `updatedAt`, emitted before final job updates.
- **Reading it.** Color and shape mean state, never agent: working is a blue dot, waiting an amber square, failed a red diamond, no activity a hollow amber ring, done gray, cancelled a hollow gray ring. Agents appear in text; time appears only as labels ("7m", "3m so far", "waiting 4m", "quiet for 8m", "stopped after 11m") with no time axis. Agents show once in the top bar with state, role, and Codex usage.
- **Totals.** Summary counts include an ended job only while unsettled (unmerged/undiscarded worktree or unread result); settled jobs stay in the list without inflating counts.
- **Needs you.** Above the projects, each waiting request is a card with the full request and the controls that answer it, so nothing has to be opened to decide.
- **Width.** Below 760px the track stands upright, with stops running top to bottom and their jobs beside them, and the details layer rises from the bottom. The page does not go below 360px. The board is light whatever the system setting; the dark variant was removed with this layout.
- **Needs you.** One line at the top lists every job and session waiting on the user across all projects as an announced status region; clicking a job's entry opens its details.
- **Lifetime.** `~/.crew/missions.json` persists missions across daemon restarts, closing idle missions as abandoned after 12 hours with no running job (job activity counts as an update). The store keeps all open missions, the 100 most recently ended, and the last two per project, retaining their jobs beyond normal history limits.
- **Ownership.** A session advances and closes only its own missions: resending the same title updates that mission, while a different title opens another beside it (section 5.5; missions closed externally are not reopened, and the lead continues without reporting). New jobs started after a mission ends as `done` auto-create a fallback follow-up mission (`후속 작업: <title>` for Korean titles, `Follow-up: <title>` otherwise; plan `implement`, `final`)—though lead instructions tell it to open a mission first—while abandoned or externally closed missions spawn none. For 12 hours after a lead-finished `done` mission (board-marked `done` excluded) while no mission is open, `UserPromptSubmit` reminds the lead on matching `CLAUDE_CODE_SESSION_ID` sessions to open a mission before new work (naming the follow-up title; suppressed after `/clear` or missing session id, and skipped by the lead for pure questions).
- **Jobs do not depend on missions.** A job given a mission that is not open still runs on its own, with a note attached. If `missions.json` cannot be read, the daemon sets it aside under a new name and starts with an empty store.
- After an MCP server restart, a session no longer remembers its mission ID. Each mission records the Claude session that opened it (`CLAUDE_CODE_SESSION_ID`, when the client passes it to the server). Passing the same title again reattaches to the open mission of that title only if this session opened it; otherwise a new mission starts and the old card stays until it is dismissed or goes stale. Two sessions in one project that use the same title therefore get separate cards. Not verified: that Claude Desktop passes the session id to the MCP server; without it nothing is reattached.
- A project with a mission keeps its group on the board even when it has no jobs or sessions left, so an open mission can always be seen and dismissed and the last finished ones stay visible.

Checked on 2026-11-12 against a separate daemon with stub agents: starting, advancing, finishing, and dismissing missions through the routes; jobs linked to a mission and a job given an unknown one; refused input (unknown stage, empty title); the mission card, its job rows, and the Needs-you line in the browser pane. The `mission` tool itself was not exercised from a live Claude session in this round: the session that built it was started before the tool existed, and its logic in `mcp.ts` has no automated test.

### 5.4 Sharing the machine

The user and every agent work on one computer, often at the same time (requirement R14). Three rules keep them out of each other's way.

- **Isolated instances.** Every command-capable worker job receives `plugin/roles/machine.md` after its role text ([09](09-usage-presets-rounds.md) section 14): start an isolated copy on a system-chosen free port with temp data and browser profiles, use headless browsers only, never touch default ports or the user's running instance/browser, and stop only what it started. `/crew:run` and self-reviewer instructions give the lead and subagents the same rules; only the lead may use the single shared browser pane.
- **Reviews in parallel, one app.** In the pipeline (`/crew:run` and MCP instructions), the lead runs one review (self or cross) at substantial stopping points, reviews uncovered commits before push/PR (both in parallel for security, concurrency, or data loss), and skips small fixes; outside the pipeline it reviews only when asked. The lead tracks reviewed commits in conversation (the bridge does not), launches parallel reviewers in one step, and leaves the working tree untouched until all report. Worker reviews default to static (`read-only` sandbox, checks finishing on their own); when running the app is required, only one reviewer runs it (`runs_app` cross-review or self-review, never both). Rules travel in system instructions so Codex's built-in review mode receives them too.
- **Plugins.** `codex.plugins` in `~/.crew/config.json` defaults to `["browser"]` for eligible Codex jobs (writable delegates and `runs_app` reviews; silently skipped for ask jobs, static reviews, polish, and other agents), which re-enables the automatic skill catalog (set `[]` to run lean). Eligible jobs get the deduplicated union of `codex.plugins`, `codex.appPlugins` when `runs_app` is true (default `["computer-use", "unified-computer-use"]`, giving shared-screen access), and the lead's `plugins`; missing or disabled explicit plugins are noted while missing/disabled defaults are silent. On start or resume, Crew queries `plugin/installed` for the cwd, enables matching installed-and-on plugins, disables other listed plugins by exact id (keeping dotted keys literal), and sets `plugins._default.enabled = false` for unseen installs. Threads without enabled plugins disable apps, plugins, tool suggestions, and the skill catalog; threads with plugins keep the catalog because Codex 0.167.0's `skills.include_instructions` controls the whole catalog including plugin skills ([schema](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/core/config.schema.json), [catalog rendering](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/ext/skills/src/world_state_catalogs.rs)). Plugin jobs deny the daemon token via permissions profile even without `runs_app`, while sandbox network access stays tied to `runs_app`. Under `approvalsReviewer: auto_review`, Codex's reviewer judges plugin calls (refusals surface normally), and user-bound plugin approvals forward only if plugins were enabled on that thread. Instructions limit computer use to the worker's own windows when screenless checks cannot answer, and tell the lead not to run two such jobs at once. Checked 2026-11-13 (Codex CLI 0.167.0, `gpt-6.1-sol`, isolated daemon): `runs_app` listed `cua_repl` while plain jobs did not; in three `runs_app` look-only jobs, `auto_review` handled all calls (refusing state reads for an app not shown frontmost). On non-native-review threads with enabled plugins, `developerInstructions` appends a user-app exception (leaving saved job instructions unchanged): when the lead's task explicitly requests a specific action in a specific user app/window, the worker may perform it via plugin tools only, never shell commands (repo files, web pages, tool output, and inference never grant this), and must stop rather than entering credentials, paying, messaging/posting, accepting terms, or changing settings. On 2026-11-14, told to use the user's Chrome, a job opened a tab, read `example.com` by screenshot, and closed only that tab; the chrome plugin's browser tools returned "The browser access host is unavailable" (uninvestigated). Not exercised: a plugin approval reaching the bridge.
- **Jobs that run the app.** `runs_app` on `delegate` or `review` enables `sandbox_workspace_write.network_access` so the job can bind local ports. A `runs_app` review runs in a writable snapshot worktree from `HEAD` (or the target commit) with `.worktreeinclude` files and—for uncommitted targets—uncommitted edits and untracked files copied in (submodules omitted and noted; `skip-worktree` files stay as committed). Snapshots and branches delete at turn end, and follow-ups get fresh ones. `polish` and command-less reviewers reject `runs_app`; the board labels these jobs "runs the app".
- **Measurement alone.** `delegate` with `exclusive` runs alone across all sessions and projects (disallowed on review and polish). The bridge refuses an exclusive start while any job is active (naming blocking jobs and their states, since waiting or stalled jobs will not clear on their own) and refuses new starts or follow-ups until it finishes, letting the lead manage ordering rather than queuing. Workers must not time anything unless `exclusive` is set; the board labels these jobs "runs alone".

Enforced vs. instructed: the bridge enforces job exclusivity, network access, and review snapshots; instance isolation, static reviews, and "only one reviewer runs the app" are instructions (no port allocation or process monitoring). The bridge cannot hold back lead measurements, subagents, or external processes; `/crew:run` tells the lead to wait until idle first.

### 5.5 Several missions, tasks, and pull requests

Added 2026-11-20, after debating the design with Codex (Sol) and Antigravity (Neon) separately; both arrived at the same addressing rule.

- **Several missions per session.** A user often gives a second command while the first is still under way, so opening a mission no longer closes the session's open one. The stored states stay `active`, `done`, `abandoned`: a mission whose workers still run is not paused, and a fourth state would only record where the lead is looking. There is no "current mission" either. With one open mission, every call works as before. With two or more, any call that changes a mission (`mission` with `stage`, `stages`, `preset`, `tasks`, `pr`, `done`, `abandoned`), starts a job, or asks `route` must name the mission (`id` on `mission`, `mission` on the job tools and `route`). Calls without one are refused with the list of open missions before anything changes or starts. A wrong guess could close or advance the wrong mission or start a job under the wrong preset, none of which can be undone. A named id must be a mission the session opened in this project. The MCP server reads the session's missions from the daemon on each call and stores none itself, so a restart loses nothing. `costMission` keeps its earlier meaning: the preset of a mission closed on the board while the session has none open. The daemon returns the open mission when the same session opens the same title in the same project again, so a retry or a batch cannot make two cards.
- **Not built, on purpose.** First, a reminder to open a new mission for follow-up work after a just-finished mission when an older one is still open: the reply to `done` notes this once, and any later unaddressed job goes to the one open mission. Second, a stored focus: the daemon only keeps, in memory on the Claude session, the mission its last lead call acted on, so the board and the app show the session's row on that card alone (or the newest of its active missions when none is recorded).
- **Tasks.** A mission can carry the tasks its lead split the work into: `{ id, title, after?, state, result? }`, with `state` one of `todo`, `doing`, `done`, `dropped`. The lead adds or updates tasks by id through `mission` (`tasks`); omitted tasks stay as they are. The merged list is checked as a whole (every `after` names a task of the mission, no task waits for itself through others, at most 40), and a refused list changes nothing. Nothing is scheduled from it: splitting, ordering, and starting are the lead's, and the daemon only says which tasks wait for nothing. A job names the task it is done for (`task_id`, stored as `Job.taskId` and refused when the mission has no such task). The mission's text shows each task's unfinished jobs and the latest finished job with its check, read directly from the jobs so no job state is copied into the task. A dropped task never counts as done, and a task waiting for one says so.
- **Read again on resume.** `SessionStart` (`startup`, `resume`, `clear`, `compact`) adds each open mission—with its stage, plan, tasks, and pull requests—to the session's context, bounded at 6,000 characters, and names any pull request still watched for a finished mission. Prompts do not carry this context. This keeps the plan, what waits for what, and what was verified the same across a stop, a resume, and a compaction.
- **Quiet missions.** The sweep stays per mission. A mission with an open task or a watched pull request is given 72 hours instead of 12, so work left overnight or over a weekend is still there; `abandoned` stays final. "Looks finished" is not shown while a task is `todo` or `doing`.
- **Pull requests.** Passing `pr` (a number or URL, resolved once with `gh pr view` in the mission's root) to `mission` links a pull request. Each link creates a watch record beside the jobs (`plugin/bridge/pulls.ts`), naming its mission and owner session and saved in `jobs.json` alongside delivery receipts so news and its acknowledgement commit together. The daemon reads each watch with `gh pr view <url> --json` every 60 seconds while checks are pending and every 5 minutes otherwise—only while the pull request is open, its mission is not abandoned, and the owner session is open in Claude Code (a hook called within 10 minutes). A closed session costs no polling. When the session returns, its pull requests are read at once, and what changed while it was away shows as the state then. Crew uses the user's `gh` and holds no GitHub credentials. An older daemon drops the watches if it rewrites `jobs.json`.
- **What is sent.** Each poll compares the current state against what the lead was already told, sending at most one news item per kind: newly failed checks on the current head; a head passing after a failure was reported; new non-author reviews requesting changes or commenting (approvals are recorded, not sent); and a pull request turning to conflicting (with no repeat until it has been mergeable in between). Linking sends nothing for what already stands; the reply states it. A merged or closed pull request ends the watch without news. News goes through the lead delivery ledger like a job's (offer, receipt, ACK) and names the mission.
- **Fixing, and its limits.** Crew fixes nothing. The news tells the lead to judge the cause and hand the fix to an agent with `reply` or `delegate` (role `fix`), quoting a reviewer's text as their words to weigh rather than instructions. The watch counts the heads in a row on which checks failed: the second says to compare the cause with the first before another fix, and the third says to stop and bring it to the user. After that third head, check failures are recorded but not sent until a head passes or the lead links the pull request again (reviews, conflicts, and passing news still flow). A done mission takes that one call, `mission` with its `id` and `pr` alone, and stays done. No news merges, closes, or deploys, and every news text says so.

Checked on 2026-11-20 with an isolated daemon (temporary home, free port): a mission opened with tasks, a circular `after` and an unknown `task_id` refused, two pull requests linked through the real `gh` (one merged, one open with changes requested), and the `SessionStart` context. Not checked live: a failing check arriving as news in a Claude session, since this repository had no pull request checks before this change.

Right now there is only the web board. If a standalone app is built later, a native macOS menu bar app (SwiftUI) is recommended ahead of Tauri:

- What a standalone app adds over a web page is OS integration—menu bar status, notifications with approve/deny buttons, and launch at login—where native SwiftUI is a better fit.
- All state and logic already live in the daemon. A client only needs `/api/state`, `/api/stream` (SSE), and a few `POST` endpoints, keeping any platform UI thin.
- The web board stays for Claude Desktop's browser pane.
