# Delivery

The daemon keeps news for the lead and uses Claude Code hooks to wake an idle session when a job finishes or needs attention. Lead tools and hook digests offer the news until the lead echoes a receipt.

**Key files:** `plugin/bridge/daemon.ts`, `mcp.ts`, `wake.ts`, `report.ts`, `context.ts`, and `codex-lead.ts`. See [jobs.md](jobs.md) for lead tools, [missions.md](missions.md#pull-requests) for PR watches, and [daemon-api.md](daemon-api.md) for hook authentication and event formats.

## News and ownership

The daemon owns delivery state in `jobs.json`. Each job records the starting MCP server's `CLAUDE_CODE_SESSION_ID` as `lead`. Board and legacy jobs start unowned; when a session acts on a job through a Crew tool, the MCP server or wake hook adopts the job before offering news. Completions, failures (including restart recovery), lead questions, decision requests, and updates from [watched pull requests](missions.md#pull-requests) append immutable `News` snapshots with a per-subject `newsSeq`. Routine progress does not create news.

## Receipts and leases

Only an echoed receipt acknowledges news. Every lead tool accepts `ack: "<receipt>"` or an array of receipt IDs, applying acknowledgements before doing work or offering new news. Tool responses and hook digests only offer news. Receipts bind to exact `(jobId, newsSeq)` snapshots (`jobId` also holds pull-watch IDs), remain valid after the offering lease expires, and validate session ownership and revisions. `ackedSeq` tracks the contiguous acknowledged prefix, and `delivered` projects it onto event sequence numbers for legacy readers (`/delivered` no longer accepts sequence ACKs). Delivery mutations flush synchronously and roll back on save failure.

- **Offering and watcher leases.** Automatic offers share one 30-second offering lease per session and retry each news item at most twice, even across crashes or restarts. Explicit tool reads issue receipts without spending that budget. Each session has one watcher lease that lasts 60 seconds, renews during polling, and is bounded by the hook deadline. New watchers exit if a healthy watcher exists, replace one within 15 seconds of its deadline, or take over after 25 seconds of silence (or immediately if a long poll disconnects early). Generation tokens fence replaced watchers.

## Hooks and response bounds

- **Hooks.** `SessionStart` (`startup`, `resume`, `clear`, `compact`, `fork`), `PostToolUse`/`PostToolUseFailure` on Crew tools, and `Stop` arm `wake.ts watch` with `asyncRewake` (needed on `SessionStart` because Claude Desktop can end idle processes under memory pressure). A watcher that wakes the lead exits 2 with the news on stderr, and its first stdout line sets `rewakeSummary`, the line Claude Code shows the user in place of its default "Stop hook feedback" (`Crew: news from cx-…`); `rewakeMessage` in `hooks.json` heads the news for the model as Crew's, not the user's. The daemon gives no watcher to a session that leads no job or pull request watch and has no mission open: under `claude -p` an `asyncRewake` hook runs in the foreground, so a watcher armed on `SessionStart` held every headless session open for a day. A headless session that does lead work still waits in its hooks until news arrives. An open mission counts because a pull request can be linked to it through the HTTP API without the owner's hooks running. Synchronous `Stop` offers pending news as `hookSpecificOutput.additionalContext`, which continues the turn without the "hook error" label exit code 2 brings, unless `stop_hook_active` is set. That needs Claude Code 2.1.163 or later; Crew's hooks already need 2.1.139 for the `args` form. `SessionStart` and `UserPromptSubmit` inject a bounded summary of pending IDs (and open missions on `SessionStart`) via `additionalContext` without offering or acknowledging. All hooks authenticate with `~/.crew/token`, including `/api/hooks/claude`. A forked session (`/branch`, `/fork`, `--fork-session`) gets its own session ID and starts with none of its parent's jobs or missions, since the parent may go on working. It takes over a job only when one of its Crew calls names that job.
- **Timeout.** Hook timeout is 86,400 seconds (`HOOK_SECONDS`), and the watcher exits 10 seconds earlier. Killed hooks do not re-arm themselves. Persisted news remains recoverable via the next hook, `status`, or the board.
- **Response bounds.** Digests hold at most 8 snapshots (`OFFER_ITEMS`), and every MCP tool response fits within 32 KiB (`LEAD_BYTES`). Tool text is capped at 24,000 bytes (`LEAD_TEXT_BYTES`) and a report page at 16,000 bytes (`REPORT_PAGE_BYTES`), leaving omitted images on the board and in the evidence list. Read long reports with `status(job_id, report_offset: 0)` using the returned UTF-16 offset (never splitting surrogate pairs) and optional `turn`.

## Codex leads

A Codex session leads with the same lead tools, but Codex has no hook that can start a turn later, so the daemon wakes it instead (`codex-lead.ts`). Host facts are in [mcp-compatibility.md](mcp-compatibility.md#5-codex-as-a-lead-host).

- **Which sessions.** The lead MCP server learns its session from each tool call's `_meta.sessionId`, the root thread, which a subagent's calls name too. The server's first call sends `POST /api/lead/hello` with `host: "codex"`, and the daemon records the session in the delivery state's `hosts`, which is saved with the receipts. Recording a session drops the ones that lead no job or pull request and have said no hello for a week. A session not listed there is a Claude session that wakes itself. Calls that arrive together share one hello. A failed hello fails the call, and the next call tries again, because a session the daemon does not know is never woken. A Codex call without `_meta.sessionId` is refused rather than taken for the last session. A server whose session changes starts the new one with no mission tracking from the old.
- **Waking.** For each Codex-hosted session with unacknowledged news that is not inside a turn, the daemon takes an automatic offer, under the same 30-second lease as a hook watcher. It then queues a note to the thread with the app-server request `thread/queue/add`, on a short-lived `codex app-server` of its own, because the queue methods need the experimental API (`experimentalApi`), which the workers' server is not given. If that server refuses the request, the daemon runs `codex queue --thread <session> --message <note>` instead. A queued note stays in Codex until the thread runs it, so news it named is not offered automatically again; a second note would only cost the lead an empty turn. Once the lead has acknowledged all the news a note named some other way (a tool response or the Stop hook), the daemon deletes the note with `thread/queue/delete`, so the note leaves no pending message and no turn for news already read. Only notes `thread/queue/add` queued can be taken back, and the daemon tracks them in memory only. A request or command that has not finished in 30 seconds is ended (`execTimed` in `rpc.ts`). On Windows that takes the `codex` its `cmd.exe` shim started, by `taskkill /T`, since Node's own timeout ends only the shim (if `taskkill` fails, only the shim is ended); elsewhere the command runs in its own process group, which is ended as a whole. A failed command gives the offer back and is tried again 30 seconds later, doubling up to every 10 minutes while it keeps failing, so the news can still wake the lead once Codex recovers. A session keeps its record for a week after its last hello even before its first job. An open TUI or desktop thread that is idle runs the note as its next turn. A note queued during a turn waits for that turn to end, shown in the thread's composer as a pending message, and the turn's Stop hook offers the same news anyway, so the daemon queues nothing while the session's hooks say it is inside a turn (from `UserPromptSubmit` or a tool call until `Stop`, `Interrupt` or a `SessionStart` that clears the conversation; `inTurn` in `claude.ts`). A session whose main loop has been silent for 10 minutes no longer counts as inside a turn, whatever its sub-agents report, since Codex reports no failed turn, and a session whose hooks the daemon has not heard (hooks untrusted, or a daemon restarted since) is queued to as before. The note only names the subjects ("Crew has news for cx-…. Call the Crew status tool…"), and the lead reads the news with `status`, which offers it again with a fresh receipt. Windows runs the `codex queue` fallback through cmd.exe, which cannot pass the line breaks, quotes and percent signs an offer's text has. With no open session, the note stays in Codex's queue. On Codex 0.172 a thread whose last turn was interrupted held its queue until the user's next turn, even once resumed ([mcp-compatibility.md](mcp-compatibility.md#5-codex-as-a-lead-host)); the UserPromptSubmit hook names the waiting news on that turn.
- **Hooks.** Crew's Codex hooks (`plugin/hooks/codex.json`, which registration puts in the user's Codex hooks file) run `context.ts` and `wake.ts context start` on `SessionStart`, `wake.ts context` on `UserPromptSubmit`, and `wake.ts stop-json` on `Stop`. Codex's hooks also run `report.ts codex` on `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, `PostToolUse`, `SubagentStart`, `SubagentStop`, `PreCompact`, `Stop`, `Interrupt` and `SessionEnd`, since Codex's payloads carry Claude Code's fields ([board.md](board.md)). Codex has no `PostToolUseFailure`, `Notification` or `StopFailure`, so a failed turn or a usage limit is not reported from its hooks. `stop-json` offers pending news as the JSON decision `{"decision":"block","reason":…}` rather than exit code 2, which pwsh does not pass on. `start` brings the daemon up before the lead's first Crew call. A hook has the user's whole environment, while Codex starts MCP servers with a filtered one. A daemon a Codex MCP server starts says so in `/api/health` (`partialEnv`), and the next client with the whole environment (a hook, the CLI, or an app) replaces it once no job runs, unless that client's install is older (`shouldReplace` in `client.ts`). Codex runs these hooks only after the user trusts them, with **Trust Hooks** in the setup checklist or in Codex's `/hooks`; until then a Codex lead still gets the queued notes, but no news at the end of a turn or in its context.
- **The daemon a Codex MCP server starts.** Until the Crew hooks are trusted, a Codex lead's MCP server is the first client to need the daemon. Codex gives MCP servers a filtered environment (on Windows 0.170 the system variables, `APPDATA`, `LOCALAPPDATA`, `USERPROFILE`, `TEMP` and `PATH`; on macOS only `HOME` and `PATH`), so the daemon it starts reports `partialEnv`, and the next client with the whole environment (a hook, the CLI or a desktop app) replaces it once it is idle, even from another copy of the plugin. On Windows Codex also runs each MCP server in a job object that ends every process in it when Codex exits, a detached or orphaned one included, so a daemon spawned there, and its workers, ended with the lead session. There the server starts the daemon through WMI (`Win32_Process.Create`, `startOutsideJob` in `client.ts`), which leaves the job: the daemon gets the user's own environment, with only the `CREW_*` variables set over it, and keeps `partialEnv`. If WMI cannot start it, it is spawned as before. The cmd.exe that WMI starts writes the daemon's log and holds it unshared until the daemon exits, and another cmd.exe cannot redirect to it meanwhile. So a client replacing that daemon, through WMI or not, waits up to eight seconds until it can open the log, starts nothing if a daemon answers in that time, and says the log is held if it stays held. macOS needs no such step: when Codex exits it signals each MCP server's process group, which a daemon spawned `detached` has left, and when Codex is killed it signals nothing (Codex 0.172, macOS, 2026-11-25). Processes a Codex hook starts are not in such a job under the interactive app-server, but under `codex exec` they end with it (Codex 0.172, Windows, 2026-11-25), so a hook that starts the daemon on Windows also goes through WMI, without `partialEnv`. A hook's whole-environment start and an MCP server's partial one can race at a cold start; when the partial one wins, the hook replaces it as soon as it is idle.

## Stalls

For stall detection (requirement R5), a running job silent for `stallSeconds` (default 5 minutes) is marked `stalled` immediately and probed if supported. For Claude sessions, the stall timer runs only when neither the main loop nor any active sub-agent is inside a tool call.

Codex implements `probe` by reading runtime status with `thread/read` (sub-agents first) and re-reading non-active threads after 3 seconds. Active turns clear the stall silently, ended sub-agents stop blocking parent completion, and parents confirmed ended without `turn/completed` fail the job (producing failure news). Inconclusive checks or adapters without `probe` emit one `stalled` news item per stall.

Codex 0.172's generated protocol exposes `willRetry` and `additionalDetails` on error notifications (2026-11-25). In upstream Codex source at `cec14d27`, a lost connection can be retried indefinitely. Crew reports the first retry and its cause as progress. Later retries retain the cause for the status check and leave the stall clock alone. Once a retry sequence reaches the stall window, the probe reports that Codex cannot reach the model and includes the cause. Item starts, completions and deltas clear the retry sequence, as does the end of the turn. The retry check covers the job's own thread, while the probe checks sub-agents for runtime status.

## Quota events and system notifications

- Quota exhaustion emits a `limit` event from Codex `codexErrorInfo` (`usageLimitExceeded`, `sessionBudgetExceeded`, `apiKeySpendLimitExceeded`, `projectSpendLimitExceeded`, `organizationSpendLimitExceeded`), Antigravity error text, or Claude `StopFailure` (`rate_limit` or `billing_error`).
- Codex failures include `additionalDetails` when provided. Crew treats rate limits, overload, internal server errors and HTTP or stream connection errors as transient failures that can be resumed with a reply. The transient treatment of `rateLimitExceeded` follows the retry policy in upstream Codex source at `cec14d27`. Authentication failures point to `codex login`, context exhaustion calls for a fresh job with a narrower brief, and sandbox failures point to [the sandbox docs](sandbox.md). Codex 0.172's generated protocol confirms the error kinds and the object form of HTTP and stream errors (2026-11-25).
- A Codex turn stopped by the automatic reviewer produces failure news, with the refused actions listed when available. See [Automatic reviewer and refusals](approvals.md#automatic-reviewer-and-refusals).
- `waiting`, `error`, `limit`, and `stalled` (plus `done` when `notifyOnDone` is true) trigger system notifications via `osascript` on macOS or a Windows PowerShell 5.1 toast under Crew's own app identity on Windows (suppressed for waiting/completion while the native desktop app holds a heartbeat lease).

## History

- 2026-11-25: Checked on Claude Code 2.1.328 with `claude -p`: a `Stop` hook's `additionalContext` continued the turn, and the continued turn's `Stop` carried `stop_hook_active: true` and an empty `background_tasks`. With Crew installed, a `claude -p` session that led nothing hung on `SessionStart` until its watcher was killed (89 s in the check), so the daemon no longer gives such a session a watcher. The installed 2.1.328 binary accepts `rewakeMessage` and `rewakeSummary` in a hook's settings and `rewakeSummary` in its JSON output.

- 2026-11-25: The daemon queues notes through the app-server queue API and takes a note back once its news is acknowledged. A note `codex queue` left in a thread whose queue was held after an interrupted turn stayed in its composer until the user typed again, and then cost a turn for news already read.
- 2026-11-25: The daemon stopped queueing notes to a Codex session inside a turn. A lead busy with the user kept getting a pending "Crew has news" message in its composer for each job that finished meanwhile, then an extra turn for news it had often already read.
- 2026-11-25: Checked on a real Codex 0.172 host on Windows: a daemon a Codex MCP server started reports `partialEnv` and the CLI replaced it while Codex ran, and Codex skips a hook it reports as `modified`. The same checks found Codex's job object ending that daemon when Codex exits, so the server now starts it through WMI. On macOS the same daemon outlived Codex.
- 2026-11-24: Codex sessions can lead. The daemon wakes them with `codex queue`, and their Stop hook answers in JSON. Verified end to end on Windows 11 with Codex CLI 0.170.0; `codex queue` was also verified on macOS, for the TUI and the desktop app.
