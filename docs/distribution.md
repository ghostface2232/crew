# Distribution plan

Recorded 2026-11-16. Steps 1 to 4 of the order of work have shipped; recognized-publisher signing (step 5) has not. This records the direction and current state for releasing Crew to users.

## Goal

A user downloads one app from GitHub Releases, runs it, and Crew is ready: the Claude Code plugin is installed, the `crew` command works, and the app shows what is still missing. Nobody needs to clone the repository, install Node, or run `crew install`.

## Channel

GitHub Releases is the single channel. Pushing a `v<version>` tag triggers `.github/workflows/release.yml`, which builds the Windows and macOS apps and attaches them to the release.

| Platform | Artifact | Signing | Updates |
| --- | --- | --- | --- |
| Windows | `Crew-Setup-<version>.exe`, a per-user NSIS installer built by `electron-builder` (no admin rights, Start menu shortcut, uninstaller) | Unsigned. SmartScreen warns on first run; `.github/release-notes.md` explains "More info → Run anyway". A code signing certificate (for example Azure Trusted Signing) is planned | Self-updates from GitHub Releases: downloads while away, verifies SHA-256, and installs on **Update Now** ([windows-app.md](windows-app.md#updates)) |
| macOS | `Crew-macOS-arm64-<version>.dmg` (to install from) and `Crew-macOS-arm64-<version>.zip` (for the updater) | Signed with a self-signed certificate (`MACOS_SIGNING_P12`) to preserve granted folder access across updates. The 0.4.0 → 0.5.0 update kept folder access without asking again. Releases lack an Apple Developer ID and notarization. Gatekeeper blocks first launch; release notes explain System Settings → Privacy & Security → Open Anyway. Building from source (`npm run package:desktop`, Xcode 27+) avoids the block | Self-updates from GitHub Releases: downloads `.zip` while away, verifies SHA-256, and swaps the bundle on **Update Now** ([macos-app.md](macos-app.md#updates)) |

The Start menu shortcut gives the Windows app an AppUserModelID (`dev.crew.desktop`), while notifications stay with the daemon's PowerShell toasts ([windows-app.md](windows-app.md#notifications)). Joining the Apple Developer Program and acquiring a Windows signing certificate remain the steps to remove first-run OS warnings.

## The app installs the plugin

`crew install` registers the marketplace, installs `crew@crew`, and writes a `crew` shim in `~/.local/bin`. From a source checkout with Codex installed, it also runs `codex plugin marketplace add <checkout>` and `codex plugin add crew@crew` (`registerCodex` in `setup.ts`), so a Codex session can lead. Codex copies the plugin into its own cache, so run `crew install` again after changing it. Hook review is part of the [first-run checklist](#first-run-checklist). A built app registers with Codex too, through a marketplace of its own (**Codex** below). Packaged apps automate this via `plugin/bridge/setup.ts`:

1. **Each app carries a built plugin.** Registering the GitHub repository would miss the built board (`plugin/board/dist` is not committed) and let plugin and app code drift. On macOS, the packaged daemon registers the copy inside `Crew.app` (`/Applications/Crew.app/Contents/Resources/bridge`). On Windows, `setup.ts` copies the plugin and `runtime/node.exe` to `~/.crew/plugins/<version>-<build>` and registers that copy so installer updates do not replace files beneath running Claude Code sessions.
2. **The plugin runs on the app's runtime.** macOS bundles standalone Node (`Contents/Resources/runtime/node`, `scripts/build-desktop.mjs`); Windows bundles `runtime/node.exe` (`scripts/build-electron.mjs`) because a hook command cannot set `ELECTRON_RUN_AS_NODE`. `linkCommand` in `setup.ts` points `~/.local/bin/crew` (and `.cmd`/`.mjs` shims on Windows) at that runtime.

With `CREW_HOME` unset, a packaged daemon checks `~/.crew/setup.json` (`registered()`). Whenever its `root`, `version`, or `build` differs, or it is not `complete`, it runs `claude plugin marketplace add <root>`, runs `claude plugin install crew@crew` or `claude plugin update crew@crew` if needed, and rewrites the `crew` shim (leaving a source-checkout `crew` marketplace alone). A copy older than the one on record skips all of this at startup while the newer copy's folder still exists: after an update, an already-open session can start a daemon from the previous copy, which must not register itself over the new one or prune it. Asked for by the user, through the setup checklist's repair or `crew install`, the older copy is registered: that is a downgrade on purpose. On Windows, startup checks `registrationMoved()` before pruning unused copies and re-registers if Claude Code rewrote the marketplace path. It defers pruning if it could not check the path. The WMI launcher preserves an unset `CREW_HOME` so a default-profile daemon still performs these checks. With an explicit `CREW_HOME`, startup skips registration, pruning, and that check. Use `crew install` or the setup checklist’s repair action to register explicitly. The marketplace and the command in `~/.local/bin` belong to the user across all Crew homes.

**Codex.** Where `codex` is installed, the same registration also installs `crew@crew` in Codex, so a Codex session can lead (`registerCodex()` in `setup.ts`). A source checkout registers its own folder. A built copy cannot: Codex copies only the plugin folder into its cache and drops symbolic links, and it does not substitute `${PLUGIN_ROOT}` in MCP arguments, so the app's runtime beside the plugin folder is out of reach ([mcp-compatibility.md](mcp-compatibility.md#5-codex-as-a-lead-host)). So the registration writes a marketplace of its own under `~/.crew/codex/marketplace` (`codex-plugin.ts`) and registers that instead:
- **MCP server.** It starts as the app's runtime on the compiled `mcp.js`, both named by absolute path. It has no `cwd`, so it runs in the session's folder.
- **Hooks.** Crew's hooks go in the user's own Codex hooks file, `hooks.json` in `CODEX_HOME` (`~/.codex` by default), beside any hooks of the user's, and not in the plugin, whose manifest points Codex at an empty `hooks/codex-plugin.json` (without one Codex would read Claude Code's `hooks/hooks.json`). Each hook runs `~/.crew/codex/bin/lead-hook <script> <args>` (`lead-hook.cmd` on Windows), not the `hook` an earlier Crew wrote for its plugin hooks, which an older copy registering again would write back. The launcher is rewritten at each registration to run the current build's script on its runtime, in the same process, so the script's output and exit status reach Codex unchanged. A source checkout's launcher runs the `.ts` scripts of Codex's installed copy of the checkout, at the `Installed plugin root:` that `codex plugin add` prints, as its MCP server does, so switching the checkout's branch changes neither until `crew install` runs again. It runs them on the `node` in `PATH`; on Windows `lead-hook.cmd` sets `NoDefaultCurrentDirectoryInExePath`, since cmd.exe would otherwise run a `node.exe` in the session's project folder first. Registration takes out every Crew handler, one whose command starts with the quoted launcher as `codexHooks` writes it, wherever it is, and puts Crew's groups where the first group holding one stood, so the event, group and index Codex keys each hook by stay put and no handler is left twice. A handler the user added to Crew's group stays, in a group after Crew's. When Crew's handlers in the file are already the ones registration would write, the file is left as it is, so registering again moves no hook, the user's in a mixed group included. A file that is not a hooks file is left as it is and reported. The file is written in place rather than replaced, so it keeps a symbolic link (a link whose target is missing gets the target written), its permissions, and on Windows its access control list.
- **What the launcher does instead of the plugin.** Hooks in the user's file outside the plugin would run whether or not Crew's plugin is, so the launcher runs a hook only while Codex's `config.toml` in the hook's `CODEX_HOME` has Crew's plugin on (`crewPluginOn`): a `plugins."crew@crew"` table or key, its `enabled` not false, and the `plugins` feature not turned off. Turning the plugin off or removing it (which deletes the table) turns the hooks off. The check reads comments, quoted keys, dotted keys and inline tables, but not multi-line strings. It runs none for a Crew worker, whose `codex app-server` the daemon starts with `CREW_CODEX_WORKER` (`adapters/codex.ts`), as the worker turns Crew's plugin off. Once the app's runtime or the script is gone, it exits 0. The entries themselves stay in `hooks.json` until the user deletes them; with `~/.crew/codex` deleted too, Codex reports each hook failing to start.
- **Why the user's hooks file.** Codex trusts a plugin's hooks against their definition and a hash of its whole copy of the plugin folder (skills, agents, manifest, MCP and hooks files), so every update would have the user trust them again. It trusts hooks in the user's hooks file against their definition alone, so with commands that stay the same from one update to the next they stay trusted: a script behind an unchanged command can change without another review (Codex 0.172 `hooks/list` and the source of `codex-rs/hooks`, Windows, 2026-11-25). Codex therefore no longer reviews each update of Crew's scripts; trusting the hooks once is trusting the Crew install that rewrites the launcher. A changed definition, such as a new timeout or a new hook, still asks for trust.
- **Existing registrations.** The folder is user-wide, like the `crew` command, whatever the Crew home. A marker file identifies a folder Crew wrote. A built copy replaces or removes only folders with that marker, and only `crew` marketplaces in Codex whose folder has it. Codex refuses to add a second folder under a name, so such a marketplace is removed first. A source checkout's `crew install` replaces any registration.
- **The setup record.** `setup.json` is written once the `crew` command's host runs this copy, so an older copy finds the newer one registered, and marked `complete` only once every installed host runs it. A failed version or marketplace query leaves registration incomplete. Only a missing executable counts as absent. Older copies are pruned on Windows only when it is complete. An incomplete record counts as unregistered, so a failed Codex install is tried again at the next start, and an older copy a host still points to is kept. Without Claude Code, a Codex registration alone counts, and the `crew` command follows it.

## First-run checklist

Both apps show a **Set up Crew** card at the top of the unfiltered Overview page (`SetupView.swift`, `Overview.tsx`), backed by `GET /api/setup`, `POST /api/setup/repair` and `POST /api/setup/trust-hooks` (matching `crew doctor`). It hides automatically once every item passes. Both apps poll every minute while open and each check starts five CLIs, so the daemon keeps the answer (`SetupCache` in `setup.ts`): for one minute while an item is missing or a check fails, and for ten minutes once every item passes; it always runs a new check on **Check Again**, after a repair, or after a registration. If the setup breaks while the card is hidden, the card therefore reappears within about ten minutes.

Each item confirms what is ready or says what to do next in the app's language. Hover over the message for details such as the installed version, command path, or error. `crew doctor` also prints these details.

| Item | What the app does |
| --- | --- |
| Crew plugin and `crew` command | Registers and writes shims automatically, checking Claude Code's plugin when Claude Code is installed and Codex's when only Codex is (Codex's plugin also keeps its own item below); exposes an **Install** repair button when missing |
| Claude Code and sign-in | Checks `claude --version` and, when installed, `claude auth status`; installing from `claude.com/code` and signing in (`claude auth login`) are left to the user |
| Codex CLI and sign-in | Checks `codex --version` and `codex login status`; installing and signing in are left to the user |
| Crew plugin in Codex | With Codex installed, checks `codex plugin list --marketplace crew` (the whole list also reads remote marketplaces, which can take a minute) for `crew@crew` installed and enabled at this copy's version; **Install** registers it |
| Crew hooks in Codex | Checked as soon as the Codex plugin item passes, so users can trust hooks before running their first Crew job. It asks a short-lived `codex app-server` for `hooks/list` (`codexHooksItem` in `setup.ts`) and finds Crew's hooks by event, command and hooks file rather than by key, whose spelling of the file's path is Codex's own. It passes when every Crew hook is trusted and enabled. Untrusted or changed hooks offer **Trust Hooks**; hooks missing from the file, or there more than once, offer **Install**, which registers again, unless a source checkout holds Codex's registration, which the app leaves alone: then the item points to `crew install` in that checkout; disabled hooks are left to the user to turn on in Codex. If the request fails or exceeds 10 seconds, the item points to a fresh check or manual review. |
| Antigravity CLI | Checks `agy --version` when `antigravity.enabled` is true; installing and running `agy` to sign in are left to the user |
| Job ledger | Shown only while a `jobs.json.unreadable-*` file is in the Crew home ([architecture.md](architecture.md#bridge-and-state)). The item points to `crew doctor` for the backup path and recovery instructions. |

Signing in to user accounts is never automated.

**Trust Hooks** (`POST /api/setup/trust-hooks`, `trustCodexHooks` in `setup.ts`) records the user's trust through app-server `config/batchWrite`, as Codex's own hook review does, writing each untrusted Crew hook's `currentHash` from `hooks/list` to `hooks.state."<key>".trusted_hash` in Codex's `config.toml`. Only hooks whose commands are the ones this copy writes are trusted, and only when the user selects it; registration never trusts on its own. The item's detail names the hooks file and the launcher they run. The user can instead trust them in Codex under **Settings → Hooks**, or `/hooks` in the CLI. Either way, a new Codex chat or CLI session runs them. [Codex hooks guide](https://learn.chatgpt.com/docs/hooks)

Codex keys a user hook `<hooks file>:<event>:<group>:<index>` (Codex 0.172, 2026-11-25). Codex skips modified hooks even when their previous trust records are still in its config, so the checklist uses Codex's live report to detect changes. Trust records left from when the hooks were the plugin's (`crew@crew:hooks/codex.json:…`) are inert.

## Release housekeeping

- Set `package.json`, `plugin/.claude-plugin/plugin.json`, and `plugin/.codex-plugin/plugin.json` to the release version (daemons compare versions to decide which replaces which), commit to `main`, and push a stable semver tag: `git tag v<version> && git push origin v<version>`.
- `.github/workflows/release.yml` publishes only when all checks pass: tag matching both version files; `.github/workflows/ci.yml` (`npm run typecheck` on `windows-latest` and `npm test` on both `macos-latest` and `windows-latest`); `npm run test:native` on the self-hosted ARM64 Mac runner (Xcode 27); and `node scripts/desktop.mjs smoke` on both packaged apps (`release/Crew.app` after signing checks and `release/win-unpacked/Crew.exe`). The macOS smoke has five minutes and must pass before upload. Run `Release` via `workflow_dispatch` on any branch to rehearse without publishing.
- `.github/release-notes.md` documents download links, install paths, and Gatekeeper/SmartScreen steps above GitHub's generated changelog.
- README documents both the packaged app install and source checkout development.

## Order of work

1. **Bundle plugin and runtime.** *Shipped:* `scripts/bundle-plugin.mjs` lays out the marketplace in each app and rewrites `node …/bridge/*.ts` commands to compiled `.js` on the bundled Node (`Contents/Resources/runtime/node` on macOS; `runtime/node.exe` on Windows, registered via per-build copies in `~/.crew/plugins` in `plugin/bridge/setup.ts`). It also writes `plugin/package.json` with `"type": "module"`: the compiled bridge is ES modules in `.js` files, and Node would otherwise go by the nearest `package.json` above wherever the plugin was copied, so one in the user's home folder saying `commonjs` would stop every command.
2. **First-launch registration and checklist.** *Shipped:* `plugin/bridge/setup.ts`, `~/.crew/setup.json`, `GET /api/setup`, `POST /api/setup/repair`, `POST /api/setup/trust-hooks`, `crew doctor`, and the Overview checklist card in both apps.
3. **Installers and auto-update.** *Shipped:* `electron-builder` NSIS installer + `desktop/updater.ts` on Windows; `.dmg`/`.zip` packaging + `native/Sources/Crew/Updater.swift` on macOS.
4. **GitHub Actions release workflow.** *Shipped:* `.github/workflows/release.yml` calls `.github/workflows/ci.yml`, builds macOS (self-hosted ARM64 Mac with Xcode 27 for `assets/crew.icon`) and Windows (hosted runner), smoke-tests both apps, and publishes with `.github/release-notes.md`. Pull requests also run `.github/workflows/ci.yml`, except a pull request that changes only docs (`docs/`, `research/`, `README.md`, `AGENTS.md`) or a push that adds only docs on top of a head whose CI passed; pushes to `main` are not re-checked.
5. **Signing.** *Remaining:* Windows code signing certificate and Apple Developer Program membership (Developer ID + notarization) when public distribution calls for them.
